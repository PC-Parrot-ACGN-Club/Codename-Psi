# DEC-003：待接收垃圾队列使用标量而非批次列表

**关联文档：** [得分、攻击与垃圾攻防](../design/offense-and-nuisance.md)、[Fever 循环](../design/fever-mode.md)、[TDD §5、§6](../../TDD.md)

## 背景

待接收垃圾队列需要支持精确数量、抵消、单次落下上限、双通道合并，以及确定性快照与回滚。它既可以是一个精确整数，也可以是保留来源信息的批次列表。

逐条核对已确认的规则后，没有一条需要批次结构：抵消与合并是加减法；单次上限是取小；不足一行的列序由独立的 `NuisanceDropState` 持有；「只抵消安全点开始时已有的数量」由安全点批处理的函数入口值给出，不需要持久化历史。批次能提供的是来源信息，属于额外能力而非需求。

## 决策

每个盘面通道持有一个精确整数，上限由规则剖面声明并在配置校验中检查。

批次语义完全交给事件流：表现层若需要按来源分组的动画，自行订阅 `NuisanceQueued`、`NuisanceOffset`、`NuisanceDropped` 维护表现侧副本。该副本不进入规则状态、不进入 checksum、不参与回滚。

## 依据

- [TDD §6](../../TDD.md)：要求为规则聚合根提供深拷贝快照，并在包含回滚的千 tick 连续推进后校验和一致。批次列表的大小随对局进程增长且无自然上限，与该要求冲突；标量是定长的。
- [TDD §5](../../TDD.md)：渲染实体等表现资产不进入可回滚规则状态，因此表现侧的分组副本有明确归属。
- [玩法设计 §4.2](../../gameplay.md)：精确数字是唯一真相，分级图标是投影，因此 UI 不需要规则层提供批次。

批次结构还会引入两个**进入 checksum 却玩家不可观察**的规则决定：抵消从队列哪一端消耗，以及合并时哪一侧在前。两者都不改变总量与落点，却会让不同实现产生不一致的校验和，且无法由基于可见行为的测试发现。标量不存在这两个决定。

## 备选方案

| 方案 | 适配条件 | 影响 |
| --- | --- | --- |
| 批次列表：保留每笔垃圾的来源与数量 | 规则依赖来源信息，或表现层无法自建副本 | 规则状态不定长且无上限，回滚代价随对局增长；引入两个不可观察但进入 checksum 的决定 |
| 标量（已选） | 没有规则依赖来源信息，表现层可由事件自建副本 | 状态定长、编码无歧义；来源信息只在事件流中存在 |
