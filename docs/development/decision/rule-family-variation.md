# DEC-001：规则族差异落在模块边界，不进入配置 schema

**关联文档：** [规则配置与开局规格冻结](../design/rule-configuration.md)、[PRD §2.3、§4.1](../../PRD.md)、[玩法设计 §1、§7](../../gameplay.md)

## 背景

产品范围只交付 Fever 一套竞技规则，多个竞技规则模式明确不在范围内。同时玩法契约要求剖面携带 `reference_profile`，因为同属 Fever 族的不同作品在计时等语义上并不一致。

配置结构因此要回答：是否为「将来可能出现第二套规则」预留表达。预留会在 schema 里写下产品没有做出的承诺，且预留出的抽象没有第二个取值可供检验；不预留则可能把不该合并的概念焊死在实现里，等真要分开时代价落在改动量最大的地方。

`Puyo Puyo! 15th Anniversary` 提供 13 个可选规则模式（初代、Tsu、Fever、Mega Puyo、Underwater、Non-Stop Fever、Excavation、Bomber、Ice Blocks、Spinner、Mission Puyo、Searchlight），是「规则族之间会在哪里分叉」的现成样本，可用来分辨哪些是配置差异、哪些是模块边界问题。

## 决策

每个剖面各写一个文件并自带 `RuleProfileId`，`MatchRequest` 按 id 选择。配置结构中不出现剖面数组，也不出现只有单一取值的规则族枚举。

族间差异改为落在模块边界上的接缝约束。下列约束不增加配置字段，各自以一个既有模式为证据：

| 约束 | 证据模式 |
| --- | --- |
| 攻防子系统的类型是「某方送出 N 个 X」而不是「N 个垃圾」，X 恒为垃圾球且不引入种类枚举 | Bomber（炸弹球）、Ice Blocks（冰冻块） |
| 小局开局的盘面装载与 Fever 题面装载走同一条路径 | Excavation（半满开局）、Non-Stop Fever（开局带 pending） |
| Fever 的三件事分开建模：是否处于 Fever 盘、如何进入、计时语义 | Non-Stop Fever（常驻 Fever）、15th 与 Fever 1/2 的计时差异 |
| CP 是一次查询 `(角色, 盘面模式, 连锁步) -> CP`，不是直接读角色表字段 | 初代与 Tsu 使用全族共享表；Fever 2 的 Mega Puyo Rush 另有一套表 |
| 判负与胜负结算留在规则聚合根，不散进盘面与结算代码 | Mission Puyo（胜利条件是任务计数） |
| 盘面几何来自剖面，不做常量也不做类型参数 | Mega Puyo（3×6 半场） |
| 可见性、球体尺寸与皮肤不进规则状态 | Searchlight（盘面部分可见） |

## 依据

- [PRD §2.3](../../PRD.md)：多个竞技规则模式不在产品范围内。
- [PRD §4.1](../../PRD.md)：模式选择页只提供 Fever 一种竞技规则，玩家在该页选择的是对手类型。
- [玩法设计 §1](../../gameplay.md)：一场对局以当时锁定的版本化 `RuleProfile` 为准，同一场内保持单一剖面。
- [玩法设计 §7](../../gameplay.md)：剖面携带 `reference_profile`，剖面标识本身已是契约要求。

## 备选方案

| 方案 | 适配条件 | 影响 |
| --- | --- | --- |
| 轴向枚举写入 schema：抵消语义、CP 来源、掉落来源、送出物种类等各自一个封闭枚举 | 已确定要交付第二套剖面，各轴取值已知 | 每个轴只有一个取值，抽象无从检验；schema 表达出产品未承诺的模式系统 |
| 规则族 enum：`Classic`/`Tsu`/`Fever` 各一套结构 | 族集合封闭且已知 | 非法组合无法表达，但每加一族都要改类型、校验器与全部分支，并把「只存在这三族」固化进类型 |
| 接缝约束（已选） | 只交付一套剖面，同时不希望把可分离的概念焊死 | 配置字段零增量；约束落在模块边界上，出现第二个真实取值时再引入枚举 |
