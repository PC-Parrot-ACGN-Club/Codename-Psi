# TDD：技术设计与工程约定

**文档定位：** 立项时制定的工程契约。描述技术栈、crate 边界、确定性与 CI 等开发至少应覆盖的约定；实现中可按情况调整选型与细节，调整时同步更新本文档与 [PRD](PRD.md)。  
**构建目标默认：** linux-gnu + windows-gnullvm  
**关联产品需求：** [PRD](PRD.md)  
**目标平台：** 首期 Linux、Windows；macOS 延后

## 1. 技术栈

| 范畴 | 决策 |
| --- | --- |
| 语言 | Rust `1.97.1`，edition 2024；通过 `rust-toolchain.toml` 锁定 |
| 游戏引擎 | Bevy `0.19.x`；`Cargo.lock` 锁定实际 patch 版本 |
| 渲染 | Bevy 2D 图元/网格、文字与 `Camera2d`；纯色矢量视觉 |
| UI | Bevy 原生 UI；明确的能力缺口触发专用 UI 插件评估 |
| 物理 | 自定义格子规则；不引入物理引擎 |
| 配置 | `serde` + RON：规则、角色、本机设置 |
| 本地化 | `serde` + JSON：`zh-CN` 与 `en` 文案 |
| 网络 | GGRS 回滚同步优先，UDP 传输，手动 `IP:端口` 连接 |
| 测试 | Rust 内置测试、确定性对局模拟、端到端对局测试 |
| CI | GitHub Actions：格式检查、测试、首期两个 x86_64 目标（Linux、Windows）的构建矩阵与免安装可执行产物 |

## 2. Cargo workspace

代码采用 workspace，职责边界如下：

```text
workspace/
├── crates/
│   ├── core/    # 纯规则、状态、配置模型、输入、确定性验证日志与规则测试
│   ├── client/  # Bevy 应用、渲染、原生 UI、输入、音频、AI 编排
│   └── net/     # GGRS 会话、UDP、联机握手、同步与断线处理
├── assets/
│   ├── data/         # RON 规则、角色和 Fever 题面
│   └── i18n/         # JSON 文案
└── docs/
```

- `core` 不依赖 Bevy、窗口、网络或文件系统；它使用整数格坐标、整数分数和固定 tick 表示全部可影响对局结果的状态。
- `client` 依赖 `core`，将输入转换为核心指令，在 `Update` 中更新表现层，并从核心状态渲染盘面。
- `net` 依赖 `core`，为网络对局提供输入打包、会话生命周期和状态校验；客户端按需启用它。
- 依赖方向固定为 `client → core`、`net → core`。核心 crate 不反向依赖客户端或网络 crate。

## 3. 确定性模拟

- 游戏规则以 60Hz 固定 tick 运行。Bevy 的渲染和 UI 保持独立帧率，通过读取最近规则快照表现动画。
- 一个 tick 的输入为每名玩家的动作位集合：左、右、软降、硬降、顺时针旋转、逆时针旋转和菜单动作。规则核心只接收已经量化到 tick 的游戏动作。
- 所有球序列、垃圾列分配和 Fever 题面选择来自对局初始化的显式随机种子；随机数实现与版本记录进开发用确定性验证元数据（非玩家回放功能，见 PRD §2.3）。
- 状态包含盘面、活动球对、候选球、计时器、分数、垃圾队列、Fever 状态、胜负状态和 RNG 状态。相同初始状态及输入日志必然导出相同状态校验值。
- 渲染实体、声音播放、粒子、用户设置和网络 socket 均属于表现/基础设施层，避免进入可回滚规则状态。

## 4. Bevy 集成

- 使用 `States` 管理启动、主菜单、模式选择、角色选择、对局、暂停、赛果和联机连接状态。
- 对局模拟使用固定调度；输入采集、原生 UI、音频事件和渲染使用普通更新调度。对局状态改变以事件或资源桥接至表现层。
- 使用 Bevy 原生 UI 实现菜单和设置。游戏盘面、球、边框和量表使用 2D 图元/网格及文字绘制；R1 仅一种固定画布 1920 × 1080、16:9，窗口与全屏等比缩放留边，不做多预设重排。
- 键盘与手柄输入映射在客户端维护为可序列化的动作表。每个本地玩家拥有独立映射；手柄震动通过独立的效果适配层接入。
- 升级 Bevy 版本前，CI 宜先通过首期双平台构建、规则回归和最小启动冒烟测试。

## 5. 配置、本地化与持久化

- `assets/data/` 中的 RON 文件保存规则常数、颜色集合、Fever 参数/题面和角色定义。每份文件包含 schema 版本。
- `assets/i18n/zh-CN.json` 与 `assets/i18n/en.json` 采用稳定键值。缺失键回退英文，并在开发构建中记录诊断。
- 本机设置保存于平台标准的应用配置目录，内容包括语言、窗口模式、音量、键盘映射、手柄映射、震动开关、角色演出与动画强度；生效时机见 PRD §7。
- 设置、规则和文本解析发生错误时，游戏加载内置安全默认值并显示可理解的诊断；规则版本异常阻止进入联机对局。

## 6. GGRS 局域网联机原型与采用门槛

GGRS 是 R2 的首选同步方案。最终依赖版本与 `bevy_ggrs` 集成方式由兼容性原型决定。

### 6.1 原型范围

- 在 Bevy `0.19.x` 中建立两人 UDP 会话；主机监听可配置端口，加入者使用手动 `IP:端口` 连接。
- 每个 60Hz tick 提交本地输入并消费 GGRS 确认或预测的双方输入。
- 为 `core::MatchState` 提供深拷贝快照、恢复和稳定校验和；回滚后表现层按最新核心状态重建。
- 处理连接、同步、状态不一致与断线事件；断线事件交由比赛流程判定断线方负。
- 使用 GGRS 的本地同步测试会话验证回滚后的状态校验值一致。

### 6.2 采用标准

- Bevy `0.19.x`、GGRS 与集成插件可在首期双目标平台完成构建。
- 两个本地模拟端连续执行 1,000 个固定 tick，包含预测输入和至少一次回滚，最终校验和一致。
- 两台局域网设备可完成一场 BO3，操作响应、断线判负和状态不一致报告符合 PRD 验收标准。
- 原型满足标准后，将实际版本写入 `Cargo.toml`，并把网络回归测试加入 CI。原型结果驱动后续网络层选型。

## 7. 测试策略与 CI

### 7.1 本地测试

- `core` 单元测试覆盖落子、旋转、重力、消除、连锁、得分、垃圾、Fever、溢出和 BO3 流程。
- 确定性回归测试将固定的种子与输入日志映射到最终状态校验和，保护规则数值与验证样本兼容性。
- 对局模拟测试让两组合法动作或 AI 对局持续运行，验证每局必然结束且盘面保持合法。
- GGRS 原型测试覆盖快照、恢复、预测输入、回滚、校验和与断线事件。

### 7.2 GitHub Actions

- 每次推送与拉取请求执行 `cargo fmt --check`、`cargo test` 和 workspace 构建。
- 本地开发与 CI 均通过 `rust-toolchain.toml` 使用 Rust `1.97.1`，工具链升级作为独立变更并运行完整 CI 矩阵。
- 构建矩阵默认为 `x86_64-unknown-linux-gnu` 与 `x86_64-pc-windows-gnullvm`。若后续出现只能用 MSVC 满足的依赖，再评估改切或增补 `x86_64-pc-windows-msvc`。`x86_64-apple-darwin` 待 macOS 目标启用后再加入。
- Bevy 图形窗口只纳入构建与最小启动冒烟测试；规则与同步测试保持无窗口运行，确保 CI 稳定。
- **当前 CI 实现：** `ubuntu-latest` 运行 `fmt`、`test` 与 `x86_64-unknown-linux-gnu` 构建（安装 Bevy 所需系统库）；`windows-latest` 运行 `x86_64-pc-windows-gnullvm` 构建。常规流水线验证编译与测试，免安装产物打包与上传延后到发布候选阶段。
- 计划中的产物策略：为首期上述两个 x86_64 目标分别打包免安装可执行文件并上传为构建产物。每个产物包含运行游戏所需的 `assets/` 目录与启动说明；产物名称含目标平台、架构和 Git 提交短 SHA。发布标签触发正式产物构建；常规分支构建产物用于测试与验收。
