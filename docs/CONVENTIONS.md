# 文档写作规范

**适用范围：** `docs/development/`、`docs/test/`
**模板：** [development/template/](development/template/README.md)

文档只表达当前设计。演变过程、修改原因和审核历史由 git 记录承担；
文档不设状态字段——提交即表示这一轮已审核通过。

## 规则

1. **只写当前结论。** 不写审核过程、变更原因、被否决的方案、未来计划，
   不用"当前 / 原 / 目前 / 暂时 / 后续将 / 待确认"这类时间限定词。

2. **一件事只写一次。** 同一条规则第二次出现时改成链接。
   引入术语前先在 `docs/` 下搜一次：已有定义就链接到那一节的锚点，不重新展开。

3. **一个主题一份文档。** 不按调用边界拆分同一个主题；一个主题涉及多个模块时，
   在同一份文档里增加「协作」一节，而不是新开一份文档。

4. **职责排除集中在「边界」节，并写明归属。**
   写法是「本文不定义 X（X 见 <链接>）」。写不出归属的排除项直接删掉。
   区分两种否定句：描述某个输入下实际不发生什么，属于行为语义，留在行为节；
   声明本文不负责某件事，迁入边界。为对比被否决的方案而写的"不需要 X"一律删除。

5. **可判定结果写在测试稿里。** 设计文档不设「验收条件」节；
   行为节的「输出」必须是可观察的，具体断言由 [测试用例设计](test/design/README.md) 承担，
   测试稿通过「关联设计」字段建立反向链接。

6. **篇幅是信号，不是标准。** 一份文档明显长于同类其它文档时，先判断属于哪一种：
   写作重复（按规则 2、3 修文档），还是被描述的模块职责过多（改设计，不是改文档）。
   不要为了压行数删信息。

## Test Basis

设计文档的 Test Basis 只写链接 + 一句依据，不标证据状态——提交的设计都是已确认的。
测试用例保留 Confirmed / Inferred / Unknown 标记：它描述的是对**代码行为**的确信度，
不是文档审核状态。

## 本规范的止损

规则上限 6 条，新增一条须删除一条。规则不配解释段落；
需要解释才能执行的规则应改成模板里的必填节。
