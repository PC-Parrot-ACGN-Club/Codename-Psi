# 测试用例设计约定

**适用范围：** 功能开发、改动、回归与修复的测试用例设计

本目录保存测试用例设计稿。设计工作依次完成 Test Basis 分析、测试点与用例设计、文档汇总，随后进入测试实现与回归。

写作规则见[文档写作规范](../../CONVENTIONS.md)。分类规则、Concern 注册表与 Domain 注册表见[测试策略与分类标准](../README.md)。

## 1. 设计流程

| 阶段 | 目标 | 产出 |
| --- | --- | --- |
| Test Basis 分析 | 确认被测行为、证据来源和可判定结果。 | 需求理解摘要、范围、假设与待确认问题。 |
| 测试点与用例设计 | 将行为拆成可验证测试点，并形成具体用例。 | 测试点清单、分类、设计方法、风险覆盖与用例表。 |
| 文档汇总 | 组织为可审阅的 Markdown 文档。 | `docs/test/design/<功能名>.md` |

### 1.1 Test Basis 分析

先识别本轮测试性质：新功能或改动、已有行为回归、修复验证；混合任务分别记录各自依据和预期。

Test Basis 依 [测试策略与分类标准](../README.md#2-test-basis-与证据状态) 的权威顺序收集。来源冲突进入待确认问题；实现和既有测试作为行为证据记录其证据状态。

需求理解摘要使用以下模板：

```markdown
## 需求理解摘要

**功能：** <一句话描述被测行为>
**测试性质：** <新功能/改动 | 已有行为回归 | 修复验证>
**本轮范围：** <覆盖的行为、状态或流程>
**Test Basis：**
- [Confirmed] <来源链接与章节>：<规则或验收依据>
- [Inferred] <来源链接与章节>：<推断及理由>
**设计基线：** <产品目标、规则基线或当前行为基线>
**关键假设：**
- <假设及依据>
**待确认问题：**
- <会影响测试方向的问题>
**证据冲突：**
- <来源、冲突内容与审核所需决定>
```

### 1.2 测试点与用例设计

对每个测试点按以下顺序记录：

1. 拆出可观察行为、状态变化与不变量。
2. 选择最低充分 Test Level：Component → Component Integration → System。
3. 标记直接验证的 Concern，可记录多个。
4. 记录主 Domain；跨域行为补充次 Domain。
5. 选择测试设计方法并说明风险来源。
6. 使用具体数据和可判定预期结果形成正式用例。

Test Level、Concern、Domain 与优先级各自服务不同决策。分类用于范围与检索；优先级用于审核和实现排序。

### 1.3 设计方法

每个测试点记录主设计方法与风险来源。方法选择、输入模型与组合规则以[测试用例设计方法参考](techniques.md)为准。

### 1.4 风险查漏

测试点完成后，只检查与被测对象直接相关的风险领域：

| 风险领域 | 查漏问题 |
| --- | --- |
| Rules 与数值 | 公式、边界、封顶、舍入、连锁与垃圾结算是否具有直接用例？ |
| 状态与流程 | 主路径、状态迁移、重复触发、暂停、重开、赛果是否具有直接用例？ |
| Configuration | schema、版本、引用关系、规则常数和题面数据是否具有直接用例？ |
| Client 与 Input | 用户动作、输入量化、关键反馈和状态桥接是否具有直接用例？ |
| AI | 合法动作、对局推进和结束条件是否具有直接用例？ |
| Network | 握手、同步、回滚、断线和状态一致性是否具有直接用例？ |
| Determinism | 初始状态、seed、输入日志、快照恢复和校验和是否具有直接用例？ |

## 2. 文档模板

每个功能创建 `docs/test/design/<功能名>.md`，并保留所有假设、待确认问题与证据状态。用例编号与跨文件引用遵循[用例编号](#21-用例编号)。

```markdown
# 测试用例设计：<功能名>

**关联设计：** <Spec、Contract、Architecture 或 Flow 链接>
**关联实现：** <crate、模块或文件>

## 需求理解摘要

<填入阶段一摘要>

## 测试点清单

### Component — <Domain>

- <测试点>（Concern: <可选>；依据：<Test Basis>）

### Component Integration — <Domain>

- <测试点>（Concern: <可选>；依据：<Test Basis>）

### System — <Domain>

- <测试点>（Concern: <可选>；依据：<Test Basis>）

## 测试用例列表

| ID | 标题 | Priority | Test Level | Concern | Domain | 前置条件 | 操作/刺激 | 测试数据 | 预期结果 | Test Basis / 证据状态 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| TC-001 | <条件、行为与结果> | P0 | Component Integration | Determinism | Rules；Match Flow | <最小状态> | <动作序列> | <具体 seed、日志、规则版本> | <可判定结果> | [Confirmed] <来源> |

```

### 2.1 用例编号

每份测试用例设计文档独立使用 `TC-001` 起始的三位编号，不要求编号在不同文档间唯一。新增用例使用该文档下一个未使用编号；删除用例留下编号空档，不复用已有编号。

文档内引用使用局部编号 `TC-XXX`。测试代码及其它文档引用用例时，使用以下完整标识：

```text
<相对 docs/test/ 的文档路径，省略 .md>::TC-XXX
```

例如：

```text
game-infrastructure::TC-001
component/game-actions::TC-001
```

完整标识不带 `docs/test/`、`.md`、`./` 或前导 `/`，并保留文档在 `docs/test/` 下的目录层级。测试代码中的引用写作：

```rust
// component/game-actions::TC-001
```

测试函数名描述被测行为，不包含用例编号。文档移动或重命名、用例迁移到另一文档时，为目标文档分配编号并同步更新全部完整标识引用。

## 3. 字段标准

| 字段 | 编写要求 |
| --- | --- |
| 标题 | 描述条件、行为与预期结果。 |
| 前置条件 | 提供触发行为所需的最小环境和状态。 |
| 操作/刺激 | 写出构造、调用、事件或输入序列。 |
| 测试数据 | 提供明确数值、ID、seed、规则版本或 fixture 条件。 |
| 预期结果 | 提供可判定的状态、返回值、事件、界面结果或校验和。 |
| Test Basis / 证据状态 | 标明精确来源、状态和审核所需上下文。 |

## 4. 交付前检查

- [ ] 已完成需求理解摘要，并记录测试性质和 Test Basis。
- [ ] 每个测试点按最低充分范围选择 Test Level。
- [ ] Concern 只标记直接验证的横切目的。
- [ ] 每个用例记录主 Domain，跨域行为记录次 Domain。
- [ ] 测试点清单与用例表逐项对应。
- [ ] 测试数据具体，预期结果可判定。
- [ ] 假设、待确认问题和证据冲突保留在审核稿中。
- [ ] P0 聚焦少数核心路径与阻断风险。
